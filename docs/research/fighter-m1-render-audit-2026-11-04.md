### Additional native handler audit: opcodes 3, 5, 6, 15, 16, 20, 35

The XBE table at `0x2E56F0` maps these opcodes to `sub_00118950`, `sub_00117F30`, `sub_00117F70`, `sub_001180B0`, `sub_00118120`, `sub_00118320`, and `sub_001188F0`, respectively. These handler records and their parameter slots are separate: each handler advances parameter cursor `3A5978` by eight bytes; after return the dispatcher advances command-record cursor `3A597C` by low16(command) × 4. The table below distinguishes record operands from the second dword in the parameter pair (`[params+4]`).

| Opcode | Native interpretation and widths | Calls / effects |
|---|---|---|
| 3 (`118950`) | `[record+4]` is sign-extended and multiplied by resource stride; `[params+4]` is added as an address operand. It reads a **signed 16-bit** selector there, then scales it by four to index two **32-bit pointer arrays** at current-object `+0x10` and `+0x18`. The selected pointer values are dereferenced for their first **32-bit** word. | `1198C0` updates a cached pointer and calls `21C070`; `1198F0` updates another cached pointer and calls `21CC10`. The complete array extents and pointed-to object contracts are not checked here. |
| 5 (`117F30`) and 6 (`117F70`) | Source address is `[record+4] × stride + [params+4]`. `[record+0xc]` is a byte count converted to a **dword count** by `>>2`; `[record+8]` selects the destination field. Corpus examples: byte counts `4` → one dword and `0x1c` → seven dwords. | `119910` adds `0x60` to the destination selector, then calls `21B690` for count 1, `21B740` for count 4, or `21B8D0` for other counts after converting the count back to bytes (`count × 4`). The native call receives a computed source address and no local bounds check is visible. |
| 15 (`1180B0`) | Computes `[record+4] × stride + [params+4] + 0x48`; reads a **32-bit pointer** at that address, then writes the 32-bit `[record+8]` value through the loaded pointer. The parameter pair's second dword is a native address/offset operand whose interpretation depends on the opcode; the command record's `[+8]` field is separate and often a selector. Bounds checks must prove the final address and accessed span after applying the opcode-specific base/stride/operand formula. For op5/6/35, validate byte-count divisibility by four, the derived dword count and the byte span passed downstream. Op3 additionally needs a signed-short selector bounded against both pointer arrays. Op15 needs a readable four-byte pointer slot, a writable four-byte pointer target, and a readable state object; op16 needs a readable state object and first word; op20 needs a readable 64-byte matrix. These are minimum observed spans, not a complete resource schema. The native handlers do not check these bounds before use.

The downstream addresses listed above (`0x21B690`, `0x21B740`, `0x21B8D0`, `0x21CE10`, `0x21C070`, `0x21CC10`) resolve to in-image XBE code bodies in generated `recomp_0016.c`, not named ELF imports. I therefore record the exact call targets and argument shapes without assigning undocumented API names. `sub_00119910` adds `0x60` to op5/6/20 selectors before forwarding; op35 forwards its selector unchanged through `sub_00119A50`.

### Follow-up correction: selector fields, resource stride, and imported object span

The earlier sentence naming `-0xa0` as an observed negative parameter offset was wrong. In the retail token lead, `-96` (`-0x60`) is opcode 20's second command-record argument (`[record+8]`), i.e. its selector; it is not `[params+4]`. The adjacent `-92` is the next op20 selector. For the model 610 records in `logs/fighter-render-program-token-lead.json`, `[record+4]` is zero except op15, where it is 80. The parameter cursor pair remains a distinct input and can contain a relocation-backed imported pointer.

In the RM1 layout lead, the op15 cursor's second dword is the imported `__EAGL::TAR:::RUNTIME_ALLOC::UID=2896;SHAPENAME=A610,1;...` pointer at RM+`0x50`; op15 computes that pointer plus `[record+4] * 3A5758` plus `0x48`, reads a 32-bit pointer there, then writes `[record+8]` through the loaded pointer. This points the safety question at the runtime TAR object's extent at `+0x48`, not a negative in-RM offset. The neighboring RM+`0x48` slot is a different imported `GeoPrimState` runtime allocation. The XBE string catalog contains `TAR.Use` at `0x002B63BC`, but generated code has no direct xref to that string, so it does not establish the TAR allocator's object size or constructor behavior.

`sub_00114B40` sets `3A5758` from `[ebx+0xc0]` of the active model/resource root before traversing wrapper records. Primary inspection of model 610's `__Model` root confirms `+0xc0 == 0`, so its op15 record index 80 adds zero stride bytes; this reduces the observed op15 address to the imported TAR pointer plus `0x48`. Do not generalize that stride value to other roots without checking their raw field.

The op3 array base is `3A5974` (the dispatch `this` object), not the parameter wrapper: at `0x114C41`, `sub_00114B40` loads a wrapper pointer into `eax`, sets `ECX=[eax]`, and passes `eax` as the stack argument. `sub_00114FE0` stores that `ECX` object in `3A5974`, reads its first dword as the command-stream pointer, and initializes the separate parameter cursor to stack-argument+4. The op3 and op4 handlers then access `[3A5974+0x10]` and `[3A5974+0x18]`. This indirection means those runtime-object fields cannot be identified with raw RM+`0x48`/`0x50` imports from the layout lead without proving object aliasing. `sub_00117F00` (op4) independently reads the first dword behind both object fields, confirming pointer-to-pointer use but giving no extent. Op3's selector is a signed 16-bit value read through its parameter-derived address; it is then a `4*selector` index into both arrays. The native path has no selector/count check. Keep those array bounds and any shader-specific selector maximum unresolved.

The primary model 610 root schema supplies these raw field observations: `+0xc0` is scalar zero; `+0xb8`, `+0xbc`, and `+0xc4` hold local pointers to data offsets 277108, 277116, and 277168; `+0xc8` is scalar one; `+0xcc` points to the material-group data already traversed by `setup/fighter_geometry.py`. In the native active-resource loop, `sub_00114B40` directly reads the `+0xc4` pointer and tests a 16-bit value at `target + 4*index + 6`; the observed minimum span for an index `i` is through `target+4*i+8`. Its source index is read from the renderer's resource-list record, and the code does not bound it against root `+0xc8`. The audited native path does not read root `+0xb8`, `+0xbc`, or `+0xc8`; their domain meanings and pointed-to extents are not established by these accesses. The root data leads are field observations only, not a complete schema.

## Bounded compiler feasibility: retain controls, replace typed geometry

The current validators support a narrow, plausible compiler path: start from a verified retail ELF and retain its root, material groups, RM records, render-program bytes, shader-parent imports, skeleton, and relocation graph; replace only payloads and fields whose relationships are explicitly checked. This is not yet an accepted native-safe compiler. `Model`, `Geometry`, `RenderProgram`, and `Skin` all expose `runtime_ready: false`; parser fixtures are synthetic and do not test rewriting or native execution.

For each resource, the compiler would need to allocate new scalar-only stream bytes and keep every associated size/count/pointer coherent:

- Each VB export has byte size/stride/flags at `VB+4/+8/+12`, inline-data relocation at `VB+16`, and a local pointer header at `VB` whose first word is `1` and whose `header+4` relocation must point to the same data. Set size to `vertex_count * stride` (or the validated padded short-stream size), preserve supported stride/flags, and update both data relocations. The position stream determines vertex count; every non-short stream must have that count. The recognized layouts are `(12,8,4,4,2)`, `(12,4,4)`, and `(12,2,4,4)` only.
- Triangle resources have one op14 command with argument `(0,)`; its parameter pair stores index count at `parameter` and the relocation to the u16 stream at `parameter+4`. Rewrite both, keep count within budgets, and bound every index by that resource's position count. If the same program has op2, its parameter count must remain `1`, its pointer at `parameter+4` targets a 16-byte header `(index_count,0,0,0)`, so that header must be rewritten too. If op2 is absent, the parser labels draw count inherited; it does not establish runtime state sequence/effective count. A compiler must preserve the exact verified retail sequence and cannot infer a substitute header.
- A skinned resource has op31's palette-row count and pointer pair, op29's fixed argument tuple and imported `EAGLAnimationBuffer` binding, plus one op9 selector stream. The palette payload is `count*16` bytes with the validated three weights and packed bone references; op9's parameter count is the vertex selector count, and its pointer must target the short stream's inline data exactly 20 bytes after its exported VB header. Rebuild selector values for the chosen palette and ensure each maps below the palette count. The validator does not require palette row count to equal vertex count; rows are selected/shared through op9. The retail skeleton and imported animation binding must stay compatible, which numeric checks alone do not prove.
- The ELF envelope records every local/import pointer as a method-2 relocation. Moving or resizing allocations therefore requires rebuilding affected local relocation addends and all section/symbol offsets coherently; raw word patching alone would either leave stale relocations or create unvalidated aliases. Import symbols must remain explicitly resolved. If changing a texture reference, preserve the import's runtime-allocation structure and rewrite only a validated `SHAPENAME=XXXX,1;` name to a known available shape, then check it against validated texture data or a trusted baseline shape.

Keeping a retail model's number of material groups, RM resources, stream layout, parent imports, and command templates fixed makes geometry-count changes structurally tractable: update the typed ranges and their verified count/pointer fields while preserving the retail control graph. The synthetic fixtures demonstrate different vertex/index counts within those schemas, and the validators cover many malformed size, pointer, and index cases. They do not exercise an ELF rewriter, so this remains a design feasibility conclusion rather than a tested compiler capability.

Preserving an arbitrary community control layout while replacing its geometry is less supported. `Geometry` requires a coherent root material count/name list, group pointer and per-group RM wrapper populations; every wrapper must point through `RM+0x38` to one unique exported RM; RM indices and VB stream exports must form a contiguous matching set. Changing resource/material topology requires rebuilding all of those counts, string pointers, wrapper pointers, export names, and associated relocations. It also requires understanding opaque root fields and command parameters. The inspected parser explicitly does not validate all command parameter semantics or `runtime_ready`; native op3 uses separate renderer-object arrays with unknown extents/selector limits, and op5/6/15/16/20/35 consume opcode-specific source spans. Reusing community controls while changing resource count or layout therefore is not justified by the current validators.

The more defensible near-term shape is to take all non-geometry controls from a verified retail template, including its root/material/RM/shader/command/skeleton structure, then replace only typed vertex, index, palette, selector payloads and their proved count/pointer relationships. That is potentially workable when the candidate geometry can be mapped onto the template's existing resource/material layout and supported stream classes. For genuinely arbitrary community topology or shader behavior, current evidence is insufficient; a sanitizer should reject it rather than preserve opaque controls. This conclusion relies on the parser contracts and fixtures above, not on unverified native semantics or a claim that retail-template substitution alone has passed native acceptance.

## Follow-up: compiler VB layout versus native op9 setter

The compiled stream relocation scheme matches the observed op9 contract. For source mesh 0, exports `__VB:::__GPvb_8_0_V2IP_610A_alpha`, `_9_0_...`, and `_10_0_...` are at data offsets `0x120`, `0x260`, and `0x2e0`; their inline data pointers are respectively `VB+0x14` (`0x134`, `0x274`, `0x2f4`) and each pointed-to 8-byte header contains `(1, data_pointer)`. In `fighter-model610-compiled.o`, the matching template exports `_8_0_V2IP_126B_alpha`, `_9_0_...`, `_10_0_...` are at `0x43ca0`, `0x43dd0`, `0x43e40`; data is exactly `VB+0x14` (`0x43cb4`, `0x43de4`, `0x43e54`), while the header targets remain the template objects `0x24c`, `0x2d4`, `0x354` and each header's second word points to the new inline data. Each export symbol still has ELF size 4 in both files. Thus the compiler relocates the exported 20-byte descriptor and data while retaining its separate template header object; it does not need the descriptor/header object themselves to be contiguous. `Geometry.vertex_buffer`'s `header+4` equality check and the compiler's `existing['data'] == old+20` requirement cover the relationships used by the command path.

In generated native code, `sub_00118030` (XBE `0x118030`, `src/recomp/gen/recomp_0008.c`) obtains the command's stream selector from record `+8`; it computes `base = parameter_pair_second_dword + record[+4] * 3A5758 - 20`, then calls `sub_00119950(selector, base)`. `sub_00119950` reads a pointer-sized word at `base+0`, reads stride at `base+8`, and forwards `(selector, pointer, stride)` to `sub_0021BB10` (`0x21BB10`). The latter updates the renderer's per-stream cached state using the selector. This gives a concrete reason for the compiler's 20-byte subtraction adjacency and for keeping the VB base's `+0` relocation and `+8` stride intact. For the sample compiled RM0, op9 selectors 0/1/2 point to the three remapped inline data addresses above, matching the template VB exports by command ordinal despite source export IDs 8/9/10.

Within this setter chain I found no read of VB `+4` byte size, `+12` flags, `+16` inline-data pointer, export symbol name, or model-name suffix. Those fields are used by the bounded Python parser/compiler and may be consumed during earlier ELF/resource initialization, which this narrow setter trace does not rule out. Nor does this chain establish a required contiguous layout for all model resources. The native setter's indexed renderer cache has its own slot structure and is not an ELF export table. The 47 successful compile results and the model 610 combat run provide separate acceptance evidence supplied by the primary agent; the wrong red/green appearance is not explained by a missing VB descriptor field in this traced path. I found no provable omitted VB-header/name relationship from this audit; any texture/color diagnosis needs a separate TAR/material-state trace.

## Follow-up: root `+0xBC` shape-key records

Native `sub_00112310` (`0x112310`, generated `recomp_0008.c`) consumes the pointer at model-root `+0xBC`. Its helper `sub_001130A0` starts there, reads the first dword of each entry, reads an entry count at `+4`, and computes the next entry after `+8 + 4*count` bytes of pointer/value array plus an aligned variable tail. During entry processing, `sub_001131B0` reads the same 16-bit value and tests bit `i` at `tail+2+(i>>3)`. ## SHPX material text safety follow-up

`setup/fighter_xsh.py` accepts `0x6f` payloads as printable ASCII terminated by NUL, bounded to 4096 bytes and the next attachment. It does not parse or constrain the text grammar. This acceptance alone does not establish that the runtime treats the bytes as inert.

The XBE contains the SHPX magic string at `0x002D58E0` and a second `?SHPX` occurrence at `0x002E39A8`; the native extension/magic recognition neighborhood in generated `recomp_0013.c` includes `sub_001DF882` (path normalization) and `sub_001DF836` (reads 1–4 bytes and assembles the value), with caller `sub_001DF8...` comparing the result against `0x53485058`. This proves SHPX recognition, not attachment dispatch. I did not find a proven call edge from that recognition path to a decoder case for SHPX kinds `0x6f`, `0x70`, `0x7c`, or `0x69`.

There are similarly valued byte tests elsewhere, but they are not safe to label SHPX handlers: `sub_001DF714` scans 8-byte records for a low-byte `0x6f` and returns the matching record's `+8` value; callers in `sub_000A4C20`, `sub_000A4C50`, and `sub_000A4D26` then interpret returned bytes as character/numeric data. `sub_001DF775` performs the analogous scan for `0x7c`. The inspected callers obtain their records through generic object/string helpers, and no trace ties those records to an SHPX attachment chain. Thus this is evidence of generic typed-value handling in the executable, not evidence that SHPX `0x6f` instantiates an expression or runtime resource.

The expression/resource question remains open: I found neither a concrete native SHPX `0x6f` dispatch arm nor its downstream callee. Until that chain is identified, keep arbitrary `0x6f` control text outside the verified-template acceptance policy; copy only exact reviewed baseline payloads (or reject changed payloads) while continuing to allow separately validated pixel/palette edits and typed `0x70` shape-name rewrites. The validator's printable-ASCII check is a format check, not a runtime-safety proof. `0x69` annotation behavior and whether `0x7c` has effects beyond its decoded scalar likewise remain unverified.

Consequently, rewriting an op15 TAR import's `SHAPENAME` alone does not keep the model's root-`+0xBC` key synchronized: the compiled output retains the retail first key `B126` while the copied source texture binding uses A610. The existing compiler preserves all table controls, so a safe geometry compiler needs a narrowly typed key rewrite at the key-pointer target for the corresponding table entry, with the exact record layout, pointers, counts, tail bytes, and terminator preserved. This is a concrete missed data relationship and plausible source of the texture mismatch; the audited code establishes the parallel key/import values and native consumption, but I did not trace a full lookup result to the visible red/green pixels.

## Follow-up: model-resource ownership and teardown evidence

The model entrypoint in this path is `sub_00097710` (XBE `0x97710`), called by `sub_00097BD0` before `sub_00097AA0`. It stores the supplied key at `this+8`, gets a resource node through `sub_00070730`, stores that node at `this+0`, registers it with `sub_0006FDC0`, then obtains/stores another resource handle at `this+4` through the later registry calls. `sub_00070730` walks a manager-owned linked list (`next` at node `+0x6c`) comparing the query with node `+0x20`; on a match it returns the existing node, otherwise it builds a new node and child-resource links. This is name/key-based reuse evidence. The inspected code does not give a maximum number of manager nodes or prove that the manager is cleared on menu return.

There is concrete object teardown. `sub_0009DE1B` calls `sub_00097BF0`; the other destructor-like path `sub_000A6B26` does so as well. In `sub_00097BF0`, the model's `this+4` handle is released through `sub_000294D0`; the shared `this+0` node is passed to `sub_000709B0` with release flag 1 and then `this+0` is cleared. `sub_000709B0` walks several owned resource-list fields (including `+0x70`, `+0x5c`, `+0x60`, `+0x58`, `+0x44`, `+0x34`, and `+0x30`) and passes entries to `sub_0006EDC0`. That helper unlinks a matching entry from its list and runs the resource-release path (`sub_0001ABA0`, `sub_0006EB80`, `sub_00029760`, `sub_00029740`) when applicable. The destructor therefore releases per-instance associations and child handles; it is not evidence that every underlying model/TAR allocation is physically returned to the OS or that the manager cache is emptied.

The bounded code reviewed does not establish an eviction policy, a cache-size limit, GPU texture release on scene transition, or a process-lifetime memory plateau. A process-lifetime cache is acceptable only after measuring it. A meaningful check should record tracked engine-heap outstanding bytes and counts for model nodes, TAR/texture resources, and GPU allocations immediately before load, during the match, and after full return to menu; repeat the same match/character cycle many times, then repeat with a finite set of distinct resource keys. Stable post-menu live counts/bytes after the first load (or a documented one-time increase per new key followed by a plateau) would demonstrate bounded retention. RSS alone is insufficient because allocator pools can retain freed pages. No such measurement was run in this read-only audit.
