# Issue #180: save-image storage and uninstall backup

Research date: 2026-11-21. Bounded, read-only source review against the parent repository's pinned toolkit commit `d108a64c0f272da2ab29016914f473018c3e2347`. No builds, game runs, save reads, or save writes were performed. Issue #180: https://github.com/vyanhursky/DefJamFFNY-recomp/issues/180.

## Findings

- The issue's ~4.9 GB save estimate describes full logical capacity of `Partition1.img` through `Partition5.img`, not a guarantee of their current physical allocation. Pinned toolkit `src/kernel/kernel_path.c:257–264` sets Partition1 to `0x00465400` sectors, Partition2 to `0x000FA000`, and Partitions3–5 to `0x00177000` each (512 bytes/sector): 5,243,404,288 bytes total (5.24 GB decimal, 4.88 GiB). Partition0 carries the partition table and is not sized to whole-disk geometry (`:254–264`, `:272–297`).
- Sparse creation is already implemented in the pin. Win32 calls `DeviceIoControl(...FSCTL_SET_SPARSE...)` before extending each image with `SetEndOfFile` (`src/kernel/kernel_path.c:527–548`). POSIX uses `ftruncate`; the source comment says it leaves a hole and existing image contents are retained (`:938–949`). The save root is `<DEFJAM_DATA>/save` when configured (`src/main.c:793–809`).
- Sparse files are viable on normal local filesystems across all three OSes, with filesystem caveats. Windows' API marks files sparse so zero ranges need not allocate clusters; Microsoft documents filesystem support probing ([FSCTL_SET_SPARSE](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_set_sparse), [Sparse File Operations](https://learn.microsoft.com/en-us/windows/win32/fileio/sparse-file-operations)). The current code ignores the `DeviceIoControl` result, so on a volume that does not support sparse files the following EOF extension may allocate the full logical capacity. APFS supports sparse files and Apple says blocks are allocated only when written ([About Apple File System](https://developer.apple.com/documentation/foundation/about-apple-file-system)); measure other macOS volume formats. Linux `ftruncate` extends a file with zero-reading regions; whether the filesystem stores those as holes is filesystem-specific ([ftruncate(2)](https://man7.org/linux/man-pages/man2/ftruncate.2.html)). Network/FUSE/unusual filesystem behavior should be measured rather than assumed.
- The current sparse initialization does not reclaim blocks from previously allocated image files. On Windows, `FSCTL_SET_SPARSE` marks the file sparse; Microsoft specifies that already allocated clusters are not deallocated by setting the flag. On POSIX, the code only calls `ftruncate` to the existing geometry and explicitly says existing contents remain. Thus older/dense images, or images copied in a way that materialized holes, may continue occupying their allocated blocks after an update. A sparse-preserving copy or explicit verified hole-punch/recreate operation is needed to reclaim that space safely; the current code does neither.

## Raw partition image audit and backup safety

- The pin's path rules direct named `Partition1\UDATA` and `Partition1\TDATA` paths to ordinary `save/UserData` and `save/TitleData` trees (`src/kernel/kernel_path.c:53–72`). Parent `src/main.c:795–798` explicitly says this title puts saved games in TDATA. These two trees and the separate `<data>/fighter-state/unlocks.ini` sidecar must be retained. Profile files and metadata under `UserData` also carry player data; imported save handling describes the files in `docs/importing-xbox-saves.md:37–46`. Custom fighter unlocks are written in the sidecar (`src/patches/fighter_runtime.c:71–74, 281–299, 389–405`; `docs/fighter-mod-support.md:121–129`). `settings.ini` is separately promised by current uninstall UI and can remain a separate verified copy (`src/app/app_setup.cpp:838–846`).
- The source review does **not** prove that the raw partition images contain no durable Def Jam data. Toolkit comments say the runtime backs raw device paths with images because utility-drive mounting reads the partition table at offset `0x800`, and say titles may format partitions (`src/kernel/kernel_path.c:238–249, 299–310`). Bare `\Device\Harddisk0\PartitionN` paths are mapped to `PartitionN.img` (`:302–329, :621–644, :1007–1014`); `NtCreateFile` opens those backing paths as regular files (`src/kernel/kernel_file.c:240–285, 1178–1230`), and the regular `NtWriteFile` path writes the opened handle (`:403–435, 1315–1338`). The special directory-open path is used for free-space/volume queries, but that does not rule out other raw opens or writes. No Def Jam-specific raw image write caller was established by this bounded source audit. Therefore do not omit `Partition*.img` from an uninstall backup on the present evidence.
- If uninstall deletes the data folder before a Def Jam-specific raw-image write audit proves those images disposable, the conservative backup is the whole `<data>/save` tree plus `fighter-state` and `settings.ini`, verified before deletion. Make the save-tree copy sparse-preserving (or use an APFS clone where applicable), since ordinary recursive copy does not promise to preserve sparse extents and may materialize up to the images' ~5.24 GB logical size. A narrower backup may exclude images only after tracing actual Def Jam open/write callers and qualifying persistent image state; path rules alone are insufficient proof.
- Existing launch backups currently copy only `save/UserData` and `fighter-state` (`src/hooks/save_backup.cpp:4–8, 82–104`), but that is not proof the uninstall path may omit TDATA or raw partition images: launch backup has a different purpose and the title's TDATA save use is explicit.

## Uninstall behavior and opportunity

- `setup/engine.py:1413–1425, 1433–1489` removes the install/build and explicitly preserves the whole data folder. `engine.uninstall` itself does not make the issue's temporary save copy.
- The app's optional “Also delete the data folder” path copies all of `<data>/save` recursively to Documents, verifies it, and then deletes all data (`src/app/app_setup.cpp:813–848, 866–873`). That copy includes logical partition images, so the temporary space can be large and may materialize sparse holes. The UI promises saves/settings copies at `:946–953`; `src/app/README.md:29–33` documents the same flow.
- There is a concrete preservation gap: the data-delete path copies `save/` and `settings.ini`, but not sibling `<data>/fighter-state/` (`src/app/app_setup.cpp:823–846`, then deletes all data at `:866–873`). The custom unlock sidecar is lost when the player selects “Also delete the data folder.” Preserve it in the verified backup alongside save data.
- Size reporting should count allocated bytes for copies when that is what limits free space; logical file sizes alone can overstate sparse source usage and understate a dense copy's temporary allocation. If the conservative whole-save backup is used, verify copied data and ensure holes remain holes (or report/check the expected full-copy requirement) before deleting the original.
