# Issue #67: simulation and animation timing (static read)

Runtime follow-up: [the Mac measurements](issue67-pit-performance-macos-2026-10-20.md) confirmed ~60 fight steps/s in ordinary combat and identified state 7 as the Blazin' activation sequence through a GPU picture capture. The static uncertainties below record the limits of this bounded read; they are not a claim that a 30 Hz cap or a timer defect was found.

Question: does the game intentionally advance animation at 30 Hz, or on every presented frame? This read supports **neither a hard 30 Hz animation cap nor animation stepping once per render**. The fight simulation consumes a nominal 60 Hz input/tick queue. Animation clocks advance once on each fighter pass in that simulation step, scaled by game state. Rendering is downstream of a separate outer-loop iteration, which may process zero to four steps. Confidence is high for this scheduling relationship; the producer's exact 60 Hz rate and the actual macOS step throughput remain unmeasured here.

## Evidence

- `sub_00011CD0` obtains queued records through `sub_000D75E0`, processes each due step through `sub_00077040`, then runs its outer-loop tail once. The earlier call-chain analysis identifies that tail as render/present (inferred). The loop allows 0–4 simulation steps per outer iteration. See [`simulation-tick.md`](simulation-tick.md#q1-call-chain-and-where-the-fixed-step-lives), lines 19–27.
- `sub_000D75E0` checks the pending-record count at frame-object `+0x17CC`, consumes one record per step via `sub_000D7960`, and applies the four-step-per-iteration cap when `+0x1A54 == 0`. The alternative setting alternates steps but its only lifted write is initialization to zero. See [`recomp_0006.c`](../../src/recomp/gen/recomp_0006.c#L32041), especially lines 32044–32076 and 32104–32135. The ten-entry queue drops its oldest record when full (the established static analysis in `simulation-tick.md`, lines 44–59).
- The frame-record queue is initialized with a rate argument of 60 by `sub_00011CD0`; `sub_000D7DA0(60)` configures the producer timer. This is interpreted as 60 Hz from the call shape, not runtime-measured. `sub_0002C530` returns a constant 1/60-second value for screen updates, while also consulting elapsed time. See [`simulation-tick.md`](simulation-tick.md#q1-call-chain-and-where-the-fixed-step-lives), lines 20–25 and 50–59; [`recomp_0001.c`](../../src/recomp/gen/recomp_0001.c#L19967) contains `sub_0002C530`.
- A live fight step (`sub_00087700`) calls `sub_001A4900` and then `sub_001A4A30` on every pass. The latter exits early for match flags `0x60` unless override bit `0x80` is set, and otherwise loops the four fighter records at `0x3B92E0` with stride `0x12E8`, invoking `sub_001A7610` for each active fighter. See [`recomp_0004.c`](../../src/recomp/gen/recomp_0004.c#L7731), [`recomp_0012.c`](../../src/recomp/gen/recomp_0012.c#L11259) lines 11272–11321, and [`simulation-tick.md`](simulation-tick.md#q2-bits-of-the-dword-at-0x3b9054-confidence-medium-for-004008-low-for-020040080), lines 66–81.

It is reached from the per-fighter simulation loop, not from the render/present tail. See [`recomp_0012.c`](../../src/recomp/gen/recomp_0012.c#L18204), lines 18219–18261, and [`fighter-record-fields.md`](fighter-record-fields.md#field-table-offsets-from-the-record-start), lines 25–30.
- Animation time is record `+0x9C`. `sub_001A8480` adds `record+0x334 * record+0xA8 * 0x3B8F2C` once per pass, stores the resulting clock, and compares it with the clip length at `+0xA4`. This is a per-step increment; no 30 Hz divisor or fixed frame quantization appears in the update. The routine clamps/adjusts the clock at the clip boundary and handles loop behavior, so clip transition semantics remain relevant. See [`recomp_0012.c`](../../src/recomp/gen/recomp_0012.c#L20596), lines 20682–20701 and 20713–20725; field interpretations are inferred in [`fighter-record-fields.md`](fighter-record-fields.md#field-table-offsets-from-the-record-start), line 26.

See [`recomp_0012.c`](../../src/recomp/gen/recomp_0012.c#L11086), lines 11091–11098 and 11100–11127, and [`simulation-tick.md`](simulation-tick.md#q3-counters-and-time-scale-confidence-high-for-addresses-medium-for-roles), lines 99–104. Thus animation is step-timed and scaled, not advanced directly by real elapsed time.

The existing fighter sample omits animation clock `+0x9C` and speed/scale values. See [`test_telemetry.c`](../../src/hooks/test_telemetry.c#L35), lines 35–65 and [`test_telemetry.c`](../../src/hooks/test_telemetry.c#L300), lines 300–305; [`recomp_manual.c`](../../src/recomp_manual.c#L67) installs the step hook.

## Interpretation for the reported symptoms

A 60 FPS counter establishes presentation throughput only. It does not establish that 60 live-fight simulation steps, and therefore 60 animation-clock advances, occur each second. Under CPU load, a slower step-processing rate can produce 60 presentations with noticeably slower animation; a bounded queue can also discard old input records rather than catch up indefinitely. Four fighters increase work in the per-step fighter loop, which updates each active fighter's skeleton joints and invokes the model update, so the 4-player sluggishness is consistent with step throughput becoming the bottleneck. That explanation is plausible, not proven; the present measurement comparing 1v1 and FFA should settle it.

There is no evidence in the inspected path that the game deliberately quantizes animation to 30 Hz. The one possible half-rate switch is frame-object `+0x1A54`, but static analysis says it alternates the step gate only if nonzero and found only a constructor write of zero. The nominal 60 Hz producer is likewise inferred from timer setup, not confirmed under the port. A measured ~25 animation advances/s could therefore reflect the live fight stepping near 25 Hz, a changed producer/timer behavior, or a mismatch between observed animation cadence and animation-clock advancement; it is not explained by a fixed 30 Hz branch in these routines.

## Useful runtime discriminator

For the same timed interval, capture (1) presented frames, (2) `sub_00087700` entries per second, and (3) the delta of one active fighter's record `+0x9C` together with `0x3B8F2C`. Repeat 1v1 and FFA at The Pit. If step rate falls toward 25 in FFA and animation-clock delta tracks it, this is CPU/queue-limited simulation. If step rate remains near 60 but rendered motion changes only about 25 times/s, inspect render interpolation/model presentation or the exact animation clip behavior next. Also sample queue count at frame object `0x3A017C + 0x17CC` and its drop/step-gate state; account for pauses, fight setup/end states, and slow-motion scale. Existing `[TEST-STATE]` reports every 30 fight steps and can be extended to include `+0x9C`, but its coarse cadence is not by itself a frame-rate measurement.

## Timer-chain and empty-queue follow-up

The frame-record timer is a **one-shot D3D PTIMER callback chain**, rather than the title arming a periodic `KeSetTimerEx` for every tick. `sub_000D7DA0(60)` converts/stores the requested period in the frame object (`+0x1A80/+0x1A84`) and calls `sub_000D7DE0`; each callback `sub_000D7EA0` calls that rearm routine and then signals the frame event. In `sub_000D7DE0`, the due-time math uses the saved TSC schedule and current TSC, computes next time as prior scheduled time + period minus current lateness, and calls `sub_00216410` with that target. This carries the phase forward when a callback is late by less than a period, so normal callback execution lateness does not get added in full to every interval. See [`recomp_0006.c`](../../src/recomp/gen/recomp_0006.c#L33439) lines 33439–33466, [`recomp_0006.c`](../../src/recomp/gen/recomp_0006.c#L33475) lines 33475–33583, [`recomp_0006.c`](../../src/recomp/gen/recomp_0006.c#L33595) lines 33595–33615, and the explanation in [`recomp_manual.c`](../../src/recomp_manual.c#L306) lines 306–321.

The manual host implementation of `sub_00216410` makes an already-passed target immediate (`target = now + 0x28`) and logs `[TIMER] callback ... asked for a time ... past; armed at once`. That lets this chain continue after a callback arrives more than one interval late. Repeated late callbacks can still lower achieved tick rate; the deadline math prevents that lateness from accumulating as a new full delay every frame, but cannot make an overloaded host execute missed ticks retroactively. See [`recomp_manual.c`](../../src/recomp_manual.c#L324) lines 324–356. This behavior differs from the generic kernel timer fallback: `kernel_bridge.c`'s polling-table periodic timers explicitly set the next deadline to `now + period` when firing and document drift; `kernel_sync.c` uses a Windows timer queue for `xbox_KeSetTimerEx`. Those implementations are not the D3D PTIMER chain described above. See [`kernel_bridge.c`](../../tools/xboxrecomp/src/kernel/kernel_bridge.c#L3114) lines 3114–3133, 3242–3268, and 3275–3326; [`kernel_sync.c`](../../tools/xboxrecomp/src/kernel/kernel_sync.c#L382) lines 382–447.

The actual runtime PTIMER service is polled by `kernel_timer_thread` every 1 ms. `kernel_ptimer_tick` derives the guest timer count from elapsed QPC time since the PTIMER reset, checks the programmed alarm, and latches a single interrupt per changed deadline. The 1 ms polling can add service jitter, but the guest's absolute-deadline/lateness correction plus the counter advancing from a fixed QPC origin prevents the timer thread's own execution time from being accumulated as a relative delay each frame. The `RECOMP_PTIMER_TRACE=1` diagnostic reports PTIMER rate, alarm counts and the last deadline step every 5 seconds. See [`kernel_bridge.c`](../../tools/xboxrecomp/src/kernel/kernel_bridge.c#L3185) lines 3185–3195 and [`kernel_bridge.c`](../../tools/xboxrecomp/src/kernel/kernel_bridge.c#L2572) lines 2572–2592 and 2620–2672. The separate `RECOMP_VBLANK` path also advances its next deadline by the fixed period and skips far-behind ticks, but the game's frame clock is documented as PTIMER, not vblank (same file, lines 2480–2550).

When `sub_000D75E0` sees count zero at `frameObj+0x17CC`, it branches to the empty path, resets its per-iteration step counter and returns zero. It does not wait inside the gate. The caller's inner step loop therefore ends and reaches the outer-loop tail/render path even with no simulation record. This confirms that presentation can continue while ticks are absent. See [`recomp_0006.c`](../../src/recomp/gen/recomp_0006.c#L32041) lines 32041–32048 and 32140–32150, plus the caller flow in [`simulation-tick.md`](simulation-tick.md#q1-call-chain-and-where-the-fixed-step-lives), lines 23–27.

For a timing discriminator, compare each callback's scheduled TSC target against its entry TSC and sample `sub_00087700` counts/s. If target lateness rises but callback cadence stays near 60 due to phase compensation, animation should continue around 60 steps/s. If observed cadence drops, inspect the count of `[TIMER]` late-target repairs, `[PTIMER]` alarm cadence, and empty-queue intervals; the queue gate itself returns immediately and allows another render. This will distinguish a drifting relative-rearm implementation from host under-service or queue loss.

## Model-pose path follow-up

The new baseline is decisive about simulation throughput: 1v1 measured 60.001 presents/s and 60.001 fight steps/s, with only two zero-step and two two-step frame deltas over 3600 frames. In that run, a 25 Hz animation cadence is not explained by missing simulation steps.

Within the requested model/pose path, I found no every-other-step gate, integer clock rounding, or visible animation LOD branch. `sub_00044660` is a thin model wrapper: it resolves the render object through `sub_000441C0`, then calls `sub_0009E4A0`. That helper selects one of two object substructures according to bit 0 of `object+0xABB4`, then passes the supplied 3D transform to `sub_000A9470`. That routine copies position/rotation components into object fields and runs its object update (`sub_000263A0`). `sub_000263A0` has object-state/flag branches (including `object+0x138` bits) that select or skip matrix-related work, but the inspected branches contain no frame parity, timestamp, or cadence check. See [`recomp_0002.c`](../../src/recomp/gen/recomp_0002.c#L10592) lines 10592–10615; [`recomp_0004.c`](../../src/recomp/gen/recomp_0004.c#L71831) lines 71831–71859; [`recomp_0005.c`](../../src/recomp/gen/recomp_0005.c#L4134) lines 4134–4167; [`recomp_0001.c`](../../src/recomp/gen/recomp_0001.c#L1152) lines 1152–1279.

The pose reader `sub_000445A0` also resolves the render object through `sub_000441C0`, then calls `sub_0009EC10`. This selects the corresponding object substructure, maps the requested joint index through the table at `0x2A54F4`, and asks `sub_000A9E50` for a 64-byte pose/matrix. `sub_000A9E50` reaches `sub_000261B0` to assemble/obtain the transform and `sub_000A9670` to copy 16 dwords to the caller's output. No keyframe index or quantization is visible in these wrapper/read-copy layers. See [`recomp_0002.c`](../../src/recomp/gen/recomp_0002.c#L10443) lines 10443–10466; [`recomp_0004.c`](../../src/recomp/gen/recomp_0004.c#L73161) lines 73161–73190; [`recomp_0005.c`](../../src/recomp/gen/recomp_0005.c#L5639) lines 5639–5676 and lines 4437–4475; [`recomp_0001.c`](../../src/recomp/gen/recomp_0001.c#L718) lines 718–747.

This stops at three calls deep. The next pose-generation boundary is `sub_000261B0`'s callees (`sub_00107230`, `sub_00022CD0` when object flag bit 0 is set, and `sub_00025180`); the animation keyframe interpolation boundary is upstream at `sub_001A77C0`, which `sub_001A8480` calls while advancing active animation channels. Those are the next bounded reads if the issue is still an animation-sampling question. The current read rules out obvious cadence gating in the model wrapper and pose-copy path, not quantization inside those deeper transform or clip-sampling routines.

## Animation-channel/interpolator boundary follow-up

`sub_001A77C0` does not read the fighter animation clock `+0x9C` or convert it to a whole frame/key index in the inspected body. It accepts an integer channel/type selector in `eax` (valid range 1–24), dispatches via tables at `0x1A7E8C`/`0x1A7E5C`, and several paths perform floating-point add/subtracts before passing float/vector arguments to `sub_00044C70` (for example [`recomp_0012.c`](../../src/recomp/gen/recomp_0012.c#L18455) lines 18481–18495 and 18707–18736). This shows fractional-valued channel parameters are preserved in this function, but does not by itself prove clip-time interpolation: the time value is not an input visible here.

The immediate path is `sub_00044C70` → `sub_00093CE0` → (when `this+0x398` is nonzero) tail-call `sub_000A6130`; the wrapper and dispatch are at [`recomp_0002.c`](../../src/recomp/gen/recomp_0002.c#L11830) lines 11830–11844 and [`recomp_0004.c`](../../src/recomp/gen/recomp_0004.c#L41306) lines 41317–41328. `sub_000A6130` is the next actual object handler/interpolator boundary and was outside this bounded read. Separately, `sub_001A8480` advances `+0x9C` with floating-point multiplication/addition and stores the float bits back, then compares that float to the clip end at `+0xA4`; no whole-key rounding occurs in that clock update ([`recomp_0012.c`](../../src/recomp/gen/recomp_0012.c#L20682) lines 20682–20691). Therefore there is no evidence here of a deliberate 30 Hz animation clock or whole-key-only clock advancement, but keyframe sampling may still quantize or interpolate downstream in `sub_000A6130` or its callees. Confidence is high about fractional clock advancement and this dispatch boundary, low about final pose sampling behavior.

Parent's first FFA measurement also held 60 presents/s and 60 fight steps/s until a 4.2-second span in which fight-step counting stopped while presentation continued at 60. That points away from steady-state step-throughput as the cause for that span, but its game state is unconfirmed. The temporary per-present pose, clock, and logic-state diagnostics in the next run should establish whether the clock froze with the step counter or whether the pose/sampling path stopped changing independently.

## State-7 freeze follow-up

The new runtime trace strongly matches a deliberate `CLogic` state transition rather than a timer failure. `sub_0008BE60` dispatches the value at `CLogic+0x2D820` through a state table; case 7 calls `sub_00089BC0`, whereas the ordinary state-5 route calls `sub_00087700` (the fighter/simulation update) at [`recomp_0004.c`](../../src/recomp/gen/recomp_0004.c#L18849) lines 18849–18891 and 18924–18935. In state 7's handler, no `sub_00087700` call occurs; it performs state-specific object/actor bookkeeping and can transition to state 10, while other branch conditions return it toward state 4 ([`recomp_0004.c`](../../src/recomp/gen/recomp_0004.c#L13808) lines 13823–13849, 13991–14012, 14269–14305). Thus the match screen's per-present step can continue while fighter animation clocks and joints remain frozen because the fighter step is not invoked in state 7.

The only lifted assignment setting `CLogic+0x2D820` to 7 found in the generated C is in `sub_00089B30`, reached as state 6's handler from `sub_0008BE60`. It takes a conditional event path, records an index in `+0x2D844`, calls `sub_00088E80`, clears an associated object's `+0x80`, then writes state 7 ([`recomp_0004.c`](../../src/recomp/gen/recomp_0004.c#L13779) lines 13779–13798; state-6 dispatch at lines 18959–18963). This looks like an explicit transition in the game logic, not a timer queue starvation event. The inspected lifted code does not label the transition as Blazin activation or identify its triggering event semantically, so that specific interpretation remains unconfirmed. The approximately 4.18-second length is also not derivable from this bounded path; it may be timed by a downstream handler or event/resource state. Confidence is high that state 7 intentionally bypasses ordinary fighter stepping, low on naming the in-game transition and explaining its exact duration.

## Limits

The report does not measure macOS behavior, prove the input-record timer's real period, identify the exact in-fight screen vtable, or verify how `sub_00044660` presents model state. The animation-record field names are inferred from use, though the arithmetic and call path are directly visible in lifted C.
