# Motion-core descriptor table extension audit (2026-11-04)

## Finding

Native initialization materializes exactly 141 16-byte descriptors into the fixed guest interval `[0x003B8648, 0x003B8F18)`: `0x8D0 / 0x10 = 141`. `sub_001A47B0` (`src/recomp/gen/recomp_0012.c:23347`) writes four words per row and stops when its destination reaches the literal end address `0x003B8F18`. Before that loop it derives shared address/stride/size metadata in `0x003B85D8..0x003B8644` from the input core stream. The input pointers retained in the rows point into that stream; this is a descriptor index, not self-contained row data.

The `1A47B0` callsite found in generated code is `sub_001A4D90` at `0x001A4DF1` (`recomp_0012.c` around line 24203): it calls `sub_00044170` first on the zero-initialized branch, then passes the returned input in EAX to `1A47B0`. That establishes a materialization boundary during initialization. The bounded trace did not find a matching table teardown or allocator release, so extension ownership must not assume a safe free point.

## Direct consumers

Generated-code search for the table bounds and descriptor pointer fields found four consumers, all in `recomp_0012.c`; no other generated file references these addresses:

- `sub_001A7F30` (`:31435`) reads descriptor `+0xC` at three paths (`:31492`, `:31518`, `:31551`) after selecting an indexed record through `0x003B930C` and `0x003B8654`.
- `sub_001B2090` (`:57786`) reads descriptor `+4` from `index*0x10 + 0x003B864C` (`:57805`) and copies the pointed data into the actor/motion object.
- `sub_001B4930` (`:64356`) reads descriptor `+0xC` (`:64451`, `:64465`, `:64500`) and uses shared metadata at `0x003B8614`, `0x003B8624`, `0x003B85DC`, and `0x003B85EC` to select and calculate frame data.
- `sub_001B4BA0` (`:64668`) checks a 16-bit value through descriptor `+0xC` (`:64691`); it is a marker/presence query used alongside `1B4930`.

The region rooted at `0x003B92E0` is four participant actor records, each `0x12E8` bytes; `sub_001A4D90` zeroes `0x12E8` dwords there and initializes each record at `0x003B9308 + slot*0x12E8` through `sub_001B3110` (native core index or `0xFFFFFFFF` when absent). Thus `0x003B930C` is the first record's `+0x2C` core-index field, not a pack-owned descriptor mapping. `sub_001B2090`, `sub_001B4930`, and `sub_001B4BA0` read a participant/context record's `+0x2C`, then use `coreIndex*0x10` to select a descriptor. `sub_001A7F30` derives a participant slot from its time input and uses that record's `+0x2C`. A custom-core adapter must preserve those four native actor records and route their core IDs to custom descriptor data; it does not need to extend or replace the participant array. The literal `0x003B8F18` is also read as a separate global by `sub_001BAA00`; it is not an available extension slot. Do not extend the fixed table into adjacent guest memory.

## Consumer contracts and special IDs

The following pseudocode records observed argument roles and side effects for independently implementing an adapter; it is a behavioral summary, not a copy of generated code.

- `1B2090(actor)`: obtain the descriptor's `+4` stream from `table[actor.coreIndex]` and pass it to `1A3AD0(actor+0xAE4, stream)`. Then select the seven-word auxiliary record at `0x003B9128 + actor.kind*0x1C`. If the sum of all seven words is nonzero, copy them in order to `actor+0xB34..0xB4C`; if their sum is zero, leave those seven fields as they were. The call returns void. This routine consumes both a core-index selection and a distinct actor-kind selection.
- `1B4BA0(actorContext, sampleIndex)`: return false for `sampleIndex==0`. Otherwise select descriptor `+0xC` using `actorContext.coreIndex`, read the 16-bit item at `data + sampleIndex*6`, and return whether it differs from `0xFFFF`. It does not mutate the actor.
- `1B4930(outputState, actorContext, motionId)`: first save the three arguments to `outputState+0xFAC`, `+0xFB0`, and `+0xF50`, then call `1C60D0(outputState)`. Clear `outputState+0xF68`, `+0xF69`, `+0xF6A`, and `+0xFB4`; save the returned value to `+0xF58`.
  - For `motionId` 31–34, map to output-state slots 0–3 (`motionId-31`). For 38–41, map to slots 0–3 (`motionId-38`). Both ranges set `+0xF54=0xFFFFFFFF`, `+0x1020=motionId`, and `+0xF5C=motionId`; use the selected output-state word at `+0xBB8+slot*4`, add `0x8E`, scale by global stride `0x003B8614`, add base `0x003B8624`, and call `1A3630` to produce temporary data at `outputState+0xF6C`. Then inspect bit `0x80` in byte `descriptor+0xC + motionId*6 + 1` selected by `actorContext.coreIndex`; if set, set `+0xF68=1`.
  - For IDs below `0x2710` not in those two ranges—including 0–30, 35–37, and 42–9999—select descriptor `+0xC` by `actorContext.coreIndex`. Read the 16-bit item at `data + motionId*6`; store its low 12 bits to `+0xF54`, `+0x1020`, and `+0xF5C`. If its high byte is signed-negative, set `+0xF68=1`. Resolve that frame through `base=0x003B85EC` and `stride=0x003B85DC`, calling `1A3630` into `+0xF6C`; set `+0xFB4 = *(uint16_t*)(data + motionId*6 + 2) + actorContext.kind*1000`.
  - For IDs `>=0x2710` (10000 and above), set `+0xF54=0xFFFFFFFF`, `+0x1020=motionId`, and `+0xF5C=motionId`; resolve `(motionId-10000)` using `0x003B8624` and stride `0x003B8614` into `+0xF6C`. If byte `outputState+0xF71` is nonzero, set `+0xF68=1`.
  - Finally, for IDs 31–34 or 38–41, sign-extend the temporary 16-bit value at `+0xF6C` into `+0x3C0` and set bit 0 of byte `+0x926`. For every other ID, sign-extend the same value into `+0x3C0` and clear bit 0 of `+0x926`. The routine returns void.

`1A7F30` is also a table consumer. Caller `1A85A0` passes it the encoded motion value only on the `<10000` branch; ECX is `participant*1000 + localId` (the code computes quotient and remainder by 1000), not elapsed time. It selects actor record `participant`, reads its core ID from `+0x2C`, then scans six-byte WWAZ records through descriptor `+0xC`. The scan starts at byte offset `0x0C` (row 2) and reads boundary words at offsets `+2` for rows 2–124. At offset `0x2EE` (row 125) it uses synthetic bound 1000 without reading the descriptor; this is the terminating sentinel pass. It tracks the previous row index (initially 1) and last boundary, then returns the previous row's word at `descriptor+0xC+previousRow*6+4` plus `localId-lastBoundary`. If the actor record's `+0x30` equals `0x41`, the return instead uses signed `actor+0xFA6` minus `((actor[0x91A]&4)|8)/4` plus the same delta. The generated special path thus applies a 2- or 3-unit correction. Do not interpret the participant quotient as a time bucket or treat `0x003B930C` as a global core-ID-to-pack mapping.

## Core-ID assignment and other direct reads

`1A4D90` initializes four participant records from the four words at `0x003B90B8 + slot*4`. For a populated slot it calls `1B3110(record, slot, selectedId)`; otherwise it sets `record+0x28` to `0xFFFFFFFF`. `1B3110` stores its third argument as a full 32-bit value at `record+0x2C` and its second argument at `record+0x28`, then calls `1B2090`. In fighter-selection path `00087090`, the `0x003B90B8` entries are written from selected fighter/list records by loading a 32-bit value and subtracting one. This selection path has four slot iterations and bounds the destination slot against its participant-count field; neither it nor `1B3110` visibly checks the selected ID against 141 or narrows it to a byte/word. The native consumer table still has only 141 rows, so an ID above 140 is not safe unless an adapter routes it before the fixed-table dereference. The upstream SOD/file source for the selection record was not established here.

One additional confirmed actor-array read outside the four descriptor readers is `1AACA0`: when global `0x003B91A4` is nonzero, it walks records from `0x003B92E0` to `0x003BDEAC` in `0x12E8` steps. For each record whose `+0x28` is not `0xFFFFFFFF`, it reads core ID at `+0x2C`; IDs 0 and 1 enter a special path that calls `000BC8E0(0x19, slot, 0xFFFFFFFF)` and, on a valid result, calls `1AA1D0` with that actor record. This is a special-case behavior to preserve or intentionally account for in an adapter. `1AAD00` is another direct `object+0x2C` reader, but its caller/object provenance was not established in this bounded pass; it returns true only for core values 0/1 plus additional object-state checks. `1C2930` also reads a `+0x2C` field, but its generated category and arguments identify a game-audio structure, not the participant record, so it is not counted as an actor consumer.

## Narrow implementation surface

The project already supports source overrides for direct callers: defining `sub_XXXXXXXX` in `src/recomp_manual.c` excludes the generated body, and (with the pinned v0.16 lifter) direct calls reach the wrapper. Existing fighter wrappers capture guest arguments/registers, call a generated `_gen` body where retail behavior should remain, then apply project logic; `src/recomp_manual.c` around `sub_00020270` is an example. `src/patches/fighter_runtime.c` uses project-owned state for data that must outlive the call. `dev_module.c` demonstrates allocating guest-addressable storage through the guest `sub_00029680` allocator; host `malloc` pointers cannot be substituted into lifted `MEM32` reads.

For an opt-in extension, the minimal interception set is the initializer `1A47B0` plus all four direct consumers above. Keep the original 141-row table intact. The initializer-side adapter must construct a separately guest-allocated descriptor/index sidecar, preserve the native shared metadata, and publish it only after complete validation. Consumer overrides should delegate retail indices to their `_gen` implementations and route custom indices through the sidecar. This is enough to avoid a generic `MEM`/`XBOX_PTR` remapping change, which would affect every guest access and cannot make the fixed physical table safely larger. The `1B4930` body is 483 bytes and contains frame-selection/control flow, so this is not merely a tiny accessor swap; its custom branch needs a faithful lifted-equivalent implementation and conformance checks.

This recommendation is conditional: first establish the source format/count for custom rows; the generated initializer itself hard-stops at 141 and does not expose a count argument. No per-participant companion mapping is implied by `0x003B930C`; it is native actor state whose `+0x2C` field carries the current core index. No teardown/free timing was established, so a process-lifetime guest allocation is the only currently defensible ownership model unless a verified native teardown is found. Never borrow unused retail rows, overwrite neighboring globals, or temporarily swap retail descriptors.
