# Issue 180: setup disk use and operation budgets

Read-only code review of `setup/engine.py`, setup path consumers, the release operation policy, and issue 180. No game files were opened. The pinned toolkit submodule is `d108a64c0f272da2ab29016914f473018c3e2347`.

## Existing extracted-folder and ISO path

`Engine.extract()` already accepts either an ISO/XISO file or an extracted directory. For a directory, it verifies the required dump files, rejects symlinks, hashes every file into an input fingerprint, copies the files into a fresh `data/extract-pending-*` staging directory, verifies the result, records input/output hashes in `extraction-state.json`, then renames the staging directory to `data/extracted`. ISO extraction uses the pinned `tools/xboxrecomp` XISO reader, validates entries and bounds, stages identically, and records output hashes. Subsequent operations reuse the extraction when state and hashes agree; when `--dump` is omitted, they validate the installed extraction and its output hashes. This makes the extracted folder a potentially reusable source, but current setup still duplicates it.

`validate_locations()` requires install, data, and supplied dump to be separate, non-nested paths. Thus the current copy-from-folder workflow intentionally avoids making the user's source and mutable application data the same tree. `link_game()` creates `<version>/source/game` as a symlink/junction to `data/extracted`. `src/main.c` passes that `game` root to the Xbox file path layer; save partitions are separately redirected under `data/save`. Many tools and hooks likewise hardcode paths relative to `DEFJAM_DATA/extracted`, including analysis (`scripts/analyze.ps1`), runtime texture capture (`src/hooks/pc_settings.c`), and HD texture generation (`setup/engine.py`).

## Direct use of the user's extracted folder

The best direct-read candidate is an already-extracted directory, not an ISO. `Xiso` expects a local image and all runtime/title asset consumers expect a directory tree, so direct ISO access would require a new virtual filesystem/archive layer across runtime and tooling. Direct extracted-folder access could save roughly the duplicate extracted tree cited by issue 180 (~2.8 GB in its macOS measurement), avoid the copy and extraction staging peak, and eliminate the user's redundant copy when they already retain their extracted dump.

This is a broad path-contract migration, not a small extraction optimization. A robust design needs a canonical verified source-root recorded in installation state, with `data/extracted` retained as a compatibility alias or all consumers taught to resolve the recorded root. Verification should retain manifest checks and a stable identity/fingerprint, while avoiding hashing the whole tree on every launch. The current extraction receipt hashes every file; file count/mtime/size shortcuts would weaken integrity and need an explicit contract. Source should be treated as immutable: guest/title writes and patches must continue going to data-owned writable locations. Existing path translation and hooks need auditing for any writes beneath `game/`. Do not point `data/extracted` at arbitrary user data and then let cleanup follow it.

Migration should be opt-in or transactional: verify the external source first, update the receipt/path alias atomically, keep saves/settings/mods untouched, and leave the former copied tree until the new path is proven usable. Uninstall must remove only setup-owned artifacts and never delete the user's source folder. The current uninstall reports and preserves the data folder wholesale, and the current cleanup routines rely on ownership receipts plus controlled paths. Mods and language packs mostly take the extracted root as an input, so they should remain compatible if given the resolved root; however any external tools that assume `$DEFJAM_DATA/extracted` and tests of alternate locations need updating. Retaining a compatibility alias would reduce that migration cost, but Windows junction/symlink behavior and path validation need explicit handling.

An easier near-term reduction is to retain the canonical data copy but add a verified “already extracted folder” mode that can avoid re-copying when source equals the intended `data/extracted` (after the same full verification). This is useful for manual builds and migration but does not remove the current installer duplication by itself. A cross-volume directory cannot be safely atomically renamed into the data tree; copying is required unless the runtime is changed to consume its external location.

## Fixed 12 GiB install-drive gate

`execute()` applies the same `12 * 1024**3` minimum to every operation after resolving `auto` through `releases.policy()`. It is checked on the install volume. The data-volume gate is separate: dump size + 1 GiB + optional 15 GiB HD work allowance, plus another 12 GiB when install and data share a volume. On a shared volume, the effective minimum also includes the data allowance; it is not just the advertised 12 GiB.

Although `pipeline()` validates Analysis, Lift, and Build separately and skips a stage when its state verifies, setup does not run the pipeline inside the existing active version. `Engine.__init__()` creates a unique `-attempt-<id>` version root for every normal setup invocation. `prepare_source()` copies candidate analysis/lift artifacts (and update analysis inputs), but never copies the old build directory. Consequently `verify_build()` runs against the new attempt's `source/build/<preset>`, which is absent, and the Build stage must run for repair, update, fresh install, downgrade, and rebuild. Repair can reuse analysis and lift, but is not a no-build path under this layout.

The current code therefore provides no evidence for lowering the 12 GiB install-volume gate for repair: every operation has to produce a fresh native executable and build intermediates. Update can reuse analysis, and repair can reuse analysis plus lift, so their peak may be lower than clean install/rebuild, but the CMake build still occurs. Keep the 12 GiB requirement for all current operations unless per-platform measurements establish a lower safe build allowance. A future verified-build reuse/copy strategy could support a smaller budget, but would need to preserve isolation, avoid changing the active executable before activation, and measure the copy/staging plus rollback peak. A 1 GiB data baseline does not establish install-volume needs. Measure peak temporary and final deltas separately before changing this gate.

Also note `versions/` retains earlier builds for rollback, and `uninstall()` removes all versions under its controlled root while preserving data. Issue 180 identifies old-version retention as an unmeasured contributor. Pruning should only follow a rollback policy decision and ownership check; it is independent of safe operation-specific preflight.

## Scope and next evidence

HD textures are excluded here. Their current setup option is gated by a separate 15 GiB data-volume allowance, generates under `data/hd-work/setup-lanczos`, and records pack state under the version root. Issue 180's format/deduplication questions need a separate asset pipeline study.

Before implementation, measure clean install/update/repair/rebuild peak free-space deltas on Windows, macOS, and Linux/Deck, including same-volume and split-volume layouts and a failed-stage retry. Audit every runtime/tool consumer of `DEFJAM_DATA/extracted`, and test user-owned source preservation, uninstall, mods/language packs, symlink/junction cases, and changed-source detection. No code or runtime behavior was changed for this review.
