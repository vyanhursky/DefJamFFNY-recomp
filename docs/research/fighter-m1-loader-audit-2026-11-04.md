# M1 custom fighter model loader audit

Static audit, 2026-11-04. Scope: identify an adapter route for a genuine custom model through the existing general pack resource path, usable in selector preview and combat. No code, build, or game run was performed.

## Finding

The current native adapter cannot load a custom appearance. `setup/fighter_native.py` allows only retail-backed `appearance`, `moveset`, `voice`, and `portrait` bindings; each resource reference must exist in `RetailCatalog.bindings`, and appearance fields (`Entity`, `Model`, `Shadow`, `BodySize`, `Sex`, `Ethnicity`) are copied from a retail SOD record. The adapter report explicitly remains `runtime_ready: false` and lists `asset-runtime-acceptance` as a blocker. A semantic `appearance` resource therefore needs a native asset adapter and runtime registration; changing the SOD's Model string alone is not evidence of model discovery.

The strongest observed entry is `sub_00109F80`, called `DynamicLoader`'s ELF parser. The manual entry hook at `src/recomp_manual.c` passes the loader object to `defjam_fighter_model_input`; that probe reads the raw ELF header from the descriptor's `+0x10`. It sees the input only before section fixup, relocation, and vertex-buffer upload. This is an observation seam, not a safe substitution or ownership point. The lifted function uses an indirect allocator from `0x2E3988`, stores loader state in its descriptor, walks ELF sections, and performs later fixups. Replacing its bytes/header in place would affect every caller using that module context and risks lifetime/relocation errors.

`sub_00102130` is a four-character `SHAPENAME` resolver. Existing research traces it through a `SHAPE` table belonging to the supplied module context; it is not a process-wide registry. Thus the narrowest plausible trusted extension is the module/resource registration step that supplies the ELF/module context and its SHAPE directory, before model parsing. Add a separately owned module/resource entry with a collision-checked shape namespace and keep its lifetime alongside the consuming fighter/model owner. Do not globally rewrite the donor module or assume a new shape name is visible to all modules. The exact native registration caller and source path still need a targeted call-chain trace before implementation.

## Path and capacity evidence

There is not yet a proven model filename derivation from the SOD `Model` field or a concrete native archive entry path in the inspected evidence. The SOD model string is logged by `defjam_fighter_materialized` from object `+0x164`, but the code does not establish how it becomes a file/archive lookup. `109F80` receives an already formed loader descriptor; its ELF input pointer is at `+0x10`. Therefore do not publish a guessed filename convention as fact.

The existing general file-pack path in `src/hooks/pc_language.c` represents a target as a pipe-separated archive chain, e.g. `screens/screens.viv|screens/intMain/mainMenu.big|mainMenu.xsh`. Targets are bounded to 512 bytes, segment names use ASCII alphanumeric/underscore/hyphen/dot/slash and reject `..`; each `Pack` has `LANG_MAX_FILES` entries and the served-resource table is fixed at 16 entries. This is a useful delivery/composition mechanism for exact known archive paths, but it is not yet connected to the fighter model loader and its 16 served entries are not a demonstrated model/shape namespace capacity. `setup/fighter_archive.py` separately bounds BIG archives to 100,000 entries/512 MiB and supports additions/replacements with case-insensitive collision rejection; fighter portrait aliasing intentionally handles only exact existing movie resources and does not establish model lookup semantics.

Consequently there are two separate capacities to measure before adding resources: the host pack/served-file bounds above, and the game-side per-module SHAPE/name table plus any SOD/core-ID constraints. No audited numeric capacity for the latter was found. The character selection bindings currently support custom fighter identity and donor core routing, but that is not a model namespace allocator.

## Preview, combat, and ownership

Menu preview and combat both need the resource to resolve in the module context used by the consuming model. Existing evidence only reaches the ELF parser and shape resolver; it does not demonstrate a preview-only route, a combat route, or equivalence between their module owners. The model input hook is called on the parser and logs at most 512 observations when research SOD data is active. It does not retain or release the ELF buffer.

The existing runtime audit corrects several tempting false leads: `109F80` is not cleanup; `102130` is module-scoped; `sub_000686A0` only writes a UI flag byte at `ECX+0x4C`; and `Game.Quit`/UI transitions do not establish model or XSH teardown. A prior resource investigation found `9D340` resets an inner owner before replacement, while the four-owner destructor is proven only at process exit. XSH owner/load and collision/lifetime rules remain unproved. Any new model/module memory should therefore be treated as process-lifetime until an actual destructor and all consumers are traced; do not free it on menu clear or match transition based on current evidence.

## Follow-up trace: model property consumers (2026-11-04)

The lifted body of `sub_00020270` (generated `recomp_0000.c`, `loc_0002030F..20316`) resolves a hashed property descriptor with ID `0x6FC83815` through `sub_000BEE90`, then `sub_0001DD20`, and stores that returned pointer at `self+0x164`. The same routine reads the fighter Character's property database through `sub_000BE760`; this is the concrete path from Character data to the pointer logged as `Model` by `defjam_fighter_materialized`. This confirms `+0x164` is a resolved property value pointer, rather than an archive handle or a loader owner.

The distinct `sub_000CB930` reader in generated `recomp_0006.c` iterates a count at `self+0x160`, reads `self+0x164`, and passes that pointer with indexed `+0x15C` records to `sub_000CAB80`. There is no call chain tying its object to the Character object built in `20270`; the matching offset is a false lead for the fighter `Model` field. Another `+0x164` hit in `recomp_0000.c` is a bulk record copy, not a path reader. The other broad `+0x164` hits include unrelated structures and stack temporaries, so the literal offset alone is not a reliable type signature.

I ran `scripts/string-va.py` for `V2IP_` and model-related format strings. It maps the baseline token `V2IP_001A` to VA `0x00289730`; generated code uses that VA in `sub_0001F1E0` only as a fallback return when a lookup result is null/`-1`. That helper has one lifted caller, `sub_0008A870` at `loc_0008A9CF`, where it selects a token for a mode-specific record in a 12-entry block. This is an ID/name lookup, not the `20270` Character materialization path. The XBE also contains `CModel::_InitData m_pDynamicLoader ...`, `CModel ERROR : couldn't find a model`, and `Base Model File Name = [%s.o]` strings. `0x28ACC8` is passed by `sub_00026760` to `sub_00029680` with a 0x30-byte allocation request; the returned block is stored in its caller's `+0x128` and passed to `sub_0010A970`. Callers include `sub_00026940` and `sub_00026A00` (the latter is reached by the face cache path below). This is a real model initialization route and reaches `109F80` through `10B430`; it does not, by itself, establish the archive key/path. The `%s.o` message remains only a naming lead. The `V2IP_*` strings have no direct literal references in generated C other than the `0x289730` fallback.

The concrete DynamicLoader descriptor lifecycle is visible in three routines. `sub_0010B3E0` zeroes a 0x30-byte descriptor, writes the input buffer pointer at `+0x10` and byte length at `+0x14`, calls `109F80`, then calls `10AC20` for post-parse fixup. `sub_0010B430` initializes the same descriptor shape with extra mode/flags, calls `109F80`, and conditionally runs `10AC20`. `sub_0010B490` calls `10AA90`, then `109F00`, then invokes the descriptor's optional callback at `+0x28` and clears that field. The model initializer `sub_00026760` reaches this parser transitively: at `2679C` it calls `10B430`, stores the returned descriptor at model-owner `+0x128`, then calls `10A970` and later `10AC20`. This identifies the module descriptor and its cleanup sequence, but not the upstream resource owner supplying the ELF bytes or the lifetime of graphics/model objects retained after parse.

The requested `sub_000CB3B0`, `sub_000CB9A0`, and `sub_000CB010` bodies were also checked. `CB3B0` constructs/iterates a typed indexed table rooted at `self+0x110`, using helpers `BD3A0`, `BD4F0`, `10B3E0`, `10A8B0`, `2B960`, and `2B970`; it does not read `+0x164` or derive a model filename. `CB9A0` builds per-entry `0x80` records and calls `E9010`/`E8C30`, with no model-property read or path formatting. `CB010` builds a normalized three-part text key from a supplied name using separator `'_'` and calls `20F20`/`CAFB0`/`1ED010`/`200C41`/`200D22`; no ELF/archive load occurs in this routine. These routines do not close the gap between the model property and `109F80`.

**Actionable delta:** the model property is established as a string-like pointer returned by property lookup; do not use `+0x164` as a place to put a module pointer. `CB930` is an unrelated same-offset object until a linking call chain is found. The DynamicLoader descriptor's `+0x10` and `+0x14` are confirmed input pointer/size, and `B490` is a descriptor cleanup path. Exact filename/archive derivation remains upstream of the constructor that supplies those bytes and requires tracing that constructor into the actual archive/file API. The `Base Model File Name = [%s.o]` diagnostic suggests an `.o` naming stage but does not establish the parent archive path or whether the character's `Model` string is the `%s` argument.

## Follow-up trace: face model definition and failing cache input (2026-11-04)

The observed chain is `sub_00097BD0` -> `sub_00097710` -> `sub_00097AA0` -> `sub_00026A00` -> `sub_00026760`. `97710` keeps the fighter name at owner `+8`, formats `assets/v2ip.viv|%s_F.o` using XBE format string `0x2A406C`, and calls `sub_001E46E0` with category `0x2DBC0C`; the returned face resource is retained at owner `+4`. Separately, it hashes the fighter name using `CAA30`, calls `70730` against manager ID `0x12` (18), stores that result at owner `+0`, and passes it to `6FDC0`. `97AA0` dereferences owner `+0`, reads that model-resource descriptor's `+0x28` as a 32-bit cache key, and calls `6EE30` against manager `12CF0(0x2FB148)` to get a pointer and size. Those outputs feed `26A00` at `97AF8`.

`70730` hashes its requested name key, walks master-definition nodes via `+0x6C` and compares the name hash at node `+0x20`. If it finds no matching name, it returns zero. On a match it allocates and initializes a resource descriptor. `6FDC0` subsequently derives descriptor `+0x28` from its source definition at `6FFC4` (`MEM32(esi+0x28)=MEM32(MEM32(esi+0x50))`). `97AA0` uses that field as the resource-cache key. `6EF20` searches manager `+0x0C`'s linked entries by key at entry `+0`, returning data pointer at `+4` and size at `+8`. On a cache miss, `26A00` passes the pointer/size pair into `26760`, whose `2679C` calls `10B430` and therefore `109F80`; the created DynamicLoader descriptor is retained at model owner `+0x128`, followed by calls to `10A970` and `10AC20`. `6EC50` is a corresponding cache-registration path: it creates 0x14-byte linked entries with key at `+0`, resource pointer at `+4` (and optional size at `+8`), and links them under manager `+8`.

This makes master-definition registration the leading extension point and missing-definition failure the leading diagnosis for the observed malformed input. Primary investigation found that retail `game/assets/entity.xml` has `V2IP_001A` and `V2IP_005A` definitions with `entity/name`, `model/name`, and `texture/name`; the community `entity.xml` contains `610A` data but the earlier private diagnostic added no corresponding entity declaration. The exact XML-to-manager-18 parser and insertion chain is not yet proven from generated callsites, so treat the missing `610A` declaration explanation as a strong inference, not a verified causal finding. The face archive file `assets/v2ip.viv|%s_F.o` is a separate retained resource path and is not itself evidence that its bytes caused the cache failure.

In the active trace shared by the primary investigator, main-model name `610A` had not appeared in parser inputs before the face read; malformed pointer `0x8109EB80` showed header words `4` and `0x24`. A raw versus RefPack change altered read length but left this pointer unchanged, which weighs against compression as the cause. It is consistent with an absent or mismatched definition/cache value, but does not prove a stale pointer or establish the allocation lifetime. Preview/combat owner equivalence and retained resource destruction are still open.

## Follow-up trace: native taunt and intro resource path (2026-11-04)

The subsequent trace (`logs/run-20261104-210943.log.err`) records the custom main model ELF at `0x82187880` with the valid `0x5B928` header size after the entity declaration was added. This confirms the earlier parser failure was removed by that declaration; a later run remained in phase 0 with live fighters and an empty-camera/no-HUD scene, so that is now a separate cinematic/intro initialization issue.

`scripts/string-va.py "taunt.xml" game/default.xbe` locates the native fatal message at VA `0x2A6833`: `*** FATAL *** - Can't find taunt.xml!`. The generated parser body receives an already parsed XML object; its file-open caller/path formation was not present in the inspected generated routines, and the fatal string has no direct numeric cross-reference in `src/recomp/gen`. Therefore the error proves the native file dependency, but the exact virtual filename/path and XML loader owner remain untraced. Relevant XML tags are `tauntslist` (`0x2A6974`), `taunt` (`0x2A698C`), `intro` (`0x2A6958`), and `extro` (`0x2A6960`). In ignored generated code, `sub_000A3E20` dispatches parser variants; case 1 calls `sub_000A3830`, which walks the `tauntslist`/`taunt` entries and returns false when its lookup fails. That false return is distinct from the fatal path for a missing whole `taunt.xml`. Case 0 calls `sub_000A2A10` for the `fly_in` block; other cases parse team-extro, Blazin-KO, and animation-list blocks. The `sub_000A3E80` resource path calls this parser when its cached type at `+0x5C` is unset; after success it formats `assets/v2ta.viv|%s.viv` (format VA `0x2A6840`) and inserts a resource entry. The file load therefore selects a named animation bundle from V2TA after the XML maps a fighter name to an animation identifier.

The retail `game/assets/taunt.xml` record for `V2IP_113A` accepts names `V2IP_113A`, `V2IP_113B`, and `V2IP_113C`, mapping to `CI_113A` and `CE_113A`. It has no `V2IP_610A` record. A custom-name record mapping `V2IP_610A` to these Blaze animation identifiers is therefore required for native lookup of the inherited intro/extro, in addition to the entity declaration. This maps the fighter's model name to animation IDs; it does not itself rename the fighter model or prove why phase 0 waits.

Read-only inspection of the existing `game/assets/v2ta.viv` confirms `CI_113A.viv` and `CE_113A.viv` are present. Each contains a main ELF exporting only its `__AnimationBank:::CI_113A` or `__AnimationBank:::CE_113A`; the auxiliary cinematic ELFs export helper models named `CAM_EYE`, `CAM_TARGET`, and player-indexed `CAM_EYEp1`/`CAM_TARGETp1` or `p2`. These are camera/target helper namespaces; no `V2IP_113A` model export or import appears in those animation bundles. Together with the identical 94-bone name/index map already established for `V2IP_610A.o` and Blaze `V2IP_113A.o`, current evidence supports reusing Blaze's animation IDs without an extra fighter-model-name binding inside the cinematic bundle. It does not prove runtime actor association, animation curve compatibility, or that the unresolved phase-0 wait originates in this subsystem; the team/venue actor lookup and state-transition waiter still need tracing.

## Follow-up: taunt parser schema and filename control (2026-11-04)

The newest control reported by the primary investigator holds the entity and taunt additions constant while providing the custom `.o`, `.xsh`, and `_F.o` resources under the retail `113A` filenames and using `Model113A`; that run reaches phase 1 and completes combat with the 610A body. The independently named `610A` model run, with the same entity and taunt mappings, remains in phase 0. This establishes that the copied taunt mapping alone is insufficient to explain the phase transition. The filename/model-name substitution is a correlated difference and is the leading remaining variable; this read-only trace does not establish whether phase 0 waits for a resource keyed by that name or for another model-name-derived binding.

I checked whether the appended single-line `<taunt>` record could be rejected because it lacks newlines. `sub_000A3830` compares parsed tokens against the exact tags `taunt`, `name`, `intro`, and `extro` and checks each candidate name against the lookup name; it does not inspect line boundaries. Its token helpers `sub_0002B960` and `sub_0002B970` dispatch through `sub_0002B8F0`/`sub_0002B7C0`. The scanner advances a byte cursor, treating `>` (`0x3E`) as a token terminator; no newline-sensitive logic appears in these routines. The compact row therefore matches the parser's token model in principle, though the exact artifact bytes supplied in run 211926 were not available here to independently verify that row's placement and closing-root syntax. The retail entry confirms the accepted shape: multiple `<name>` children followed by `<intro>` and `<extro>` inside `<taunt>`.

The logs for run 211926 show the usual `assets\entity.xml` open but no `taunt.xml` open in the filesystem trace. This supports the prior caveat: `taunt.xml` appears to be loaded through a distinct mechanism or outside the hooked file path, so this log cannot prove the appended mapping was consumed. Native parser evidence says the row shape is plausible; the phase-0 versus phase-1 paired result says that mapping alone does not resolve the stall. Keep the exact taunt-file loader path and phase transition waiter open. No evidence from these runs shows that the CI/CE actor bundle must be renamed to `V2IP_610A`; the animation ELF exports and imports inspected earlier contain no such fighter-model binding.

## Follow-up: IntroExtro source is a nested NIS archive member (2026-11-04)

The earlier loose-file hypothesis was incomplete. `sub_0008ABF0` (generated `recomp_0004.c`) builds the subsystem path with format string VA `0x2A0EF8` (`%sassets/IntroExtro.xml`) at `loc_0008AD2B`, then stores the resulting string through `sub_0002B4A0` at `0x8AD52`. The same initializer sets up adjacent intro/extro resources and is called by `sub_0008BD7C` (call site at generated line 31474). This is the native `CIntroExtroSubsystem` initialization path; the `A3FA0`/`A3E80` code then parses an already resolved XML context.

The target is not the loose `game/assets/taunt.xml` copy. A read-only BIG directory scan found `assets/IntroExtro.xml` inside `game/assets/nis.viv` at archive offset 7568, compressed size 1188 bytes. It is RefPack-compressed (`10 FB` signature); decompression shows the expected `<tauntslist>` root and retail fighter `<taunt>` rows. Run 211926 logs a successful open of `assets\\nis.viv`, and the mod transport reports only `entity.xml`, `taunt.xml`, and `v2ip.viv` as served files. It logs neither a loose `taunt.xml` open nor an `IntroExtro.xml` open, consistent with the latter being consumed as a nested archive member. The exact general-pack override target is therefore `assets/nis.viv|assets/IntroExtro.xml`; editing/serving loose `assets/taunt.xml` does not change the native taunt list.

`sub_00087AF0` constructs the descriptors consumed by `sub_000A3FA0`. Its branch code writes descriptor `edi+4` before calling `A3FA0`; `A3FA0` initializes the rest of its object but leaves `+4` intact. `sub_000A3E20` later reads that preserved `self+4` and passes it to the selected XML parser, including `sub_000A3830` for kind 1. The descriptor's `+4` is a pointer into subsystem-owned arrays selected by the branch (examples include `ebx+0x2D9E4`, `ebx+0x2D974`, `ebx+0x2DA54`, and `ebx+0x2DAC4`); it is not an independently opened loose XML file. The parent's live watch (`A3E80 -> A3830` repeated over a thousand times) confirms this subsystem lookup is active, but the precise association between every descriptor branch and each tag kind still depends on that runtime watch's object contents.

This corrects the prior report's implication that the currently edited loose `game/assets/taunt.xml` file was the native source. The likely reason the taunt row had no effect is transport targeting: the row must be added to the compressed `assets/IntroExtro.xml` member within `assets/nis.viv` (or supplied as that exact archive-chain resource). No code, build, or game run was performed for this trace.

## Follow-up: native PosePaletteBank load and consumption boundary (2026-11-04)

The native face path `sub_00097AA0` loads the face ELF into its model object at `self+0x10` through `sub_00026A00`, then calls `sub_000215E0` with `ECX=self+0x430` and export key VA `0x2B72AC` (`PosePaletteBank`). `215E0` uses the normal DynamicLoader path (`10B3E0`/`10A970`), resolves this named export in the loaded module, and writes the returned pointer to the supplied owner slot on success. It calls `10B490` on both success and failure to release the temporary loader descriptor, returning false/true respectively. This proves the export is required/resolved in the face module context, not that its pointed-to bytes have been schema-validated.

The face path does **not** forward that export pointer into CModel `+0x2C0`. At `97B25`, `215E0` is called with `ECX=owner+0x430` as the output slot. Later, `97AA0` calls `24BE0` on the CModel at `owner+0x10` with three zero arguments (at `97B61`), so that face path sets CModel `+0x2C0/+0x2C4/+0x2C8` to zero. By contrast, `973D0` initializes owner `+0x430/+0x434/+0x438` to zero, then passes those three owner fields to the CModel setter at `97457`; this is a separate model initialization path.

Direct CModel-field readers checked in generated C include `24070`, `25E00`, and `263A0`. They pass the `+0x2C0/+0x2C4/+0x2C8` values by value to transform helpers (`109270` or `1074B0`); those helpers consume float/vector values and do not dereference the values as pointers. Property helpers `81550`/`81700` select among CModel `+0x2C0..+0x2F0` values and query a static property mapping through `85450`; they likewise do not walk a `PosePaletteBank` payload or check bone indices. The related `112310` walks a separate runtime transform/skeleton structure (`+0xBC/+0xC0`, records computed at 80 bytes each); it does not dereference the face export pointer and cannot establish the on-disk PosePaletteBank stride.

Accordingly, the native chain establishes symbol name, module-local resolution, and the face-owner output slot, but not a consumer of the exported payload. The global indirect-call slot at `0x2E398C` is set by `106CD0` and used generically by many call sites; it is not evidence of a PosePaletteBank type-registration table. I found no native reader of the pointed-to palette data that establishes its internal count, record stride, bone-index bounds, or face-to-body palette compatibility. The custom ELF graph notes for `V2IP_610A_F.o` (export at data `0x2364` and local relocations through `0x632`, `0x624`, `0x2352`, and `0x656`) remain payload-derived structural leads only. Keep the palette schema/bounds gate open until an actual data dereference is traced; do not approve solely from the pointer relocations or matching main-model skeleton topology.
